# QQ / SnowLuma 集成

> 本文汇总 QQ 侧的一切：SnowLuma 启动与注入、端口与 token、群/私聊监听、文件与图片归档、系统下载目录、让 QQ 端显示已接收。

## 班级 QQ 账号：多账号时选一个

一台机器上登过好几个 QQ 号时，"注入到哪个号"是必须明确的。设置页「QQ 连接 → 班级 QQ 账号」：

- 点「检测并选择账号」→ 先通过 OneBot `get_login_info` 检测当前在线的账号，
  再弹窗列出**检测到的 + 以前用过的**账号（在线的那个会标「当前在线」），选一个；
- 检测不到（OneBot 没连上）时也能从候选里选，或直接手动输入 QQ 号；
- 选择会记住（`qqAccount` + `qqAccounts`），探测时若发现**在线账号与所选不一致**会弹橙色提醒；
- 顺带补上了 **OneBot Token** 输入框（以前 `settings.json` 里有这个字段但设置页填不了，
  SnowLuma 配了 access token 就连不上）。

## SnowLuma 的协议同意（不完成它就不注入）

SnowLuma 启动后会停在 `awaiting EULA/PRIVACY consent before the panel unlocks`：
**同意之前它不会注入，OneBot 的 HTTP 服务也不会起来**。这时用户看到的现象是
"检测不到账号 / 已启动但未注入"，而原因是协议没同意——所以应用要自己把这件事做掉。

做法（在风险警告之后、真正启动之前）：

1. **先看 SnowLuma 自己记过没有**：读它 `config/consent.json` 里的 `version`，
   与我们按**它自己的算法**算出的当前版本（`sha256(id\0text\0 …)` 的 hex 前 16 位）比对；
   一致就说明用户已经在 WebUI 里同意过 → 直接跳过，不再问第二遍；
2. 否则读它安装目录里的 `EULA.md` / `PRIVACY.md`（正文原样，不转述），弹窗让用户读并选择；
3. 同意后用它的官方开关启动：环境变量 `SNOWLUMA_ACCEPT_EULA=1` + `SNOWLUMA_ACCEPT_PRIVACY=1`
   （**两个必须同时给**，只给一个会被它忽略；值只认 `1`/`true`）；
4. 记下这个版本号。协议文本一改版本就变，会重新征得同意。

版本算法是**逐字节复刻**它的实现，并用 node 按它源码独立算过一遍对照（两边同为 `dcb31a7b03a0b64d`），
所以能可靠地认出"它已经同意了"。

### 还要打开它的"自动注入"

SnowLuma 的 `config/runtime.json` 里 `hookAutoLoad` 默认是 **false**：
它只起 WebUI，**发现 QQ 进程也不会注入**（日志里只有 WebUI 那几行）。
所以点「启动」时应用会把这个开关打开（写回 `runtime.json`，保留其它字段，原子替换），
并在事件页记一条「已开启 SnowLuma 的自动注入」。想关掉在 WebUI 里改回去即可。

### 监听哪些群

默认**只监听你列出的群**，而不是该账号所在的全部群 —— 这是刻意的：班级号往往在几十个群里
（实测那个号有 43 个群，包括各种技术群），全监听会让它在无关群里也触发 AI 与通知，
既费钱又会产生莫名其妙的作业/换课。

- **「选择群…」**：从 OneBot 拉该账号的群列表（带群名与人数），**复选框多选**，不用手打群号；
  （早先用的是多选 ListBox —— Avalonia 的多选要按 Ctrl 点，看起来就像只能单选，所以换掉了）
- **「监听老师私聊」**：老师私聊发的「来一下」/作业也处理；只认老师映射里的 QQ，
  陌生人私聊一律忽略（名单为空时不做过滤）。**只监听私聊是合法配置** ——
  不选群也能开功能（那种情况下群消息一律不处理）；
- 也可以直接在输入框里手填（英文逗号分隔）；
- **「监听全部群」**开关：确实想全监听时打开（会在事件页记一条警告）。

一个坑：**群列表属于"抢到 OneBot 端口的那个账号"**。多账号时如果班级号没抢到 3000/3001，
你看到的群列表就是另一个号的（实测：另一个号只有 6 个群，班级号有 43 个）。

解决办法：设置页多账号提示旁边的 **「自动分配端口」** —— 应用会给每个账号写一组互不冲突的端口
（第一个 3000/3001、第二个 3010/3011…，改的是它自己的 `config/onebot_<uin>.json`，保留其它字段），
然后重启 SnowLuma 生效。之后**选了哪个账号就自动填哪个账号的地址与 token**，
不需要再关心端口是谁的。

### OneBot 要带 token（应用会自动读）

SnowLuma 的 OneBot HTTP/WS **默认要求鉴权**：不带 token 的请求一律
`{"status":"failed","retcode":1401,"wording":"unauthorized"}` ——
表现就是应用"检测不到账号 / 看不到在线"。

token 就写在它的配置里：`config/onebot_<uin>.json` → `networks.httpServers[0].accessToken`
（43 位随机串，每个账号一份）。

> ⚠️ **HTTP 与 WS 是两个不同的 token**：`httpServers[0].accessToken` 与
> `wsServers[0].accessToken` 各一个（实测不同）。只填 HTTP 那个时，HTTP 调用能通、
> **WS 升级会被拒 401**（SnowLuma 日志：`rejected unauthorized WebSocket upgrade`），
> 表现是应用一直"QQ 未连接（重连中…）"、**消息事件一条都收不到**。
> 应用点「检测并选择账号」会把两个 token 都填上（设置页有单独一行「OneBot WS Token」）。
> 另外**地址与 token 必须是同一个账号的**：手工把 URL 改成另一个账号的端口、token 没跟着换，
> 就会出现"HTTP 能通、WS 一直 401"（实测踩到）。应用启动时会校验这组组合，
> 不对就按 SnowLuma 的配置自动纠正，并在事件页说明。应用会**自己读出来**（地址、端口、token 一起），
并逐个账号试到能应答为止——**3000/3001 归哪个账号取决于 SnowLuma 启动时谁先登录**，
所以不能假定是哪一个，也不能让用户手抄 token。

> 另外踩过一个坑：动作调用（`get_login_info` 等）走的是反序列化，而 OneBot 返回的是
> snake_case 的 `user_id`；模型里少写 `JsonPropertyName` 就会永远读到 0，
> 于是"明明在线却检测不到账号"。事件那条路是 `OneBotParser` 手写读取，不受影响。

### 多账号：3000/3001 只能给一个号

SnowLuma 会给**每个登录的 QQ** 都开一套 OneBot 适配器，而默认端口都是 3000/3001。
于是第二个登录的账号必然 `EADDRINUSE`（`network startup degraded: failures=2`），
它就没有 OneBot 服务可用了 —— 这就是"两个号都登着，只有一个能连上"的原因。

应用现在会从 SnowLuma 的日志里读出**登录过哪些号**（`session started: UIN=`），
多于一个时给出提示，并把这些号都放进「检测并选择账号」的候选里
（不只是当前占着端口的那一个）。日志里那几类 DEBUG 行（`Event0x210 unknown subType=381/382`、
`login history sync disabled`）是无害噪音，不用管。

想两个号都接入，就在 SnowLuma 的 WebUI 里给每个账号分配不同端口；
否则建议只保留班级 QQ 登录。

### Linux 上注入的两个关卡

**第一关：ptrace 权限。**

SnowLuma 的注入是"跟踪一个已经在跑的 QQ 进程"，而 Arch 默认
`kernel.yama.ptrace_scope=1`（只允许跟踪**自己的子进程**）→ 注入必然失败，
它自己的日志里只有一行 `[Hook] load failed ... COMPONENT_LOAD_FAILED`。

```bash
sudo sysctl kernel.yama.ptrace_scope=0      # 临时放开（重启失效）

### 接管已在运行的实例

「启动」时若发现 SnowLuma 已经在跑（上次应用启动的、或用户手动启动的），
**直接接管而不是再开一个**：两个实例会抢同一个 WebUI 端口（第二个会自动换到 5100，
于是应用里显示的地址指向另一个实例），而且「停止」会停不掉真正在跑的那个。
接管后「停止」也能把它停掉（按 pid 杀进程树）。

### 不重定向它的输出

SnowLuma 会同时写自己的日志文件和 stdout。应用**不再接管它的 stdout/stderr**：
一旦应用退出，管道就断了，而它会陷入"写管道 EPIPE → 记一条错误日志 → 又写管道"的死循环
（实测把它自己的日志刷到 291MB）。要看它的输出请用设置页的「打开日志」。

为什么不用它的 HTTP 接口：`/api/agreements` 与 `/api/agreements/record-consent` 虽然存在，
但**需要先登录 WebUI**（未登录返回 401），而首次的初始密码是它每次启动随机生成、只打印在
进程输出里。抓日志里的密码太脆，环境变量是它留给自动化的正路。

> 应用**不会**替用户同意：不同意就返回、不启动，并在界面上写明"未同意协议"。

### WebUI 的登录密码

SnowLuma 的 WebUI（`http://127.0.0.1:5099`）默认**每次启动随机生成一个初始密码**，
而且这个密码**只打印到 stdout** —— 从桌面图标启动的用户根本看不到它
（它自己的日志里只有"凭据"横幅，没有密码本身）。

应用现在用它的官方环境变量 `SNOWLUMA_WEBUI_BOOTSTRAP_PASSWORD` 替用户定一个：
点「启动」时若发现它还在用初始密码（`config/webui.json` 的 `mustChangePassword=true`），
就生成一个 12 位随机密码（避开 `0/O/1/l/I`）传给它，并显示在设置页上，带「复制密码」按钮：

> 登录 WebUI：用户名 `admin`，初始密码 `xxxxxxxxxxxx`（登录后请自行修改）

也可以**自己指定**：设置页有「设置密码…」按钮，弹窗输入即可（留空 = 改回自动生成，至少 8 位 ——
SnowLuma 自己会忽略更短的值）。

> **踩过的坑**：这个环境变量只在 SnowLuma **没有 `config/webui.json`** 时才用来播种凭据
> （它源码里 `envBootstrapPassword` 那段），文件已存在就直接忽略、沿用旧哈希 ——
> 所以"改了密码、重启了、还是密码错误"。应用现在会先把那份凭据**备份成 `webui.json.bak-*` 再删掉**，
> 让它用我们的密码重新播种，并用日志里的 `credentials seeded from ...` 确认真的生效。
> 实测：`POST /api/login` 用自己设的密码返回 `{"success":true,"mustChangePassword":false}` ✓
已经改过密码（`mustChangePassword=false`）就不再插手。想手动看/重置也可以：

```bash
cd ~/.local/share/SmartClassroom/snowluma
./launcher.sh                                    # 从终端启动：密码会打印在输出里
SNOWLUMA_WEBUI_BOOTSTRAP_PASSWORD=你的密码 ./launcher.sh   # 或者自己指定
rm config/webui.json && ./launcher.sh            # 或者删掉配置，让它重新生成一个
```

### 私聊文件也能归档

SnowLuma 把**私聊文件**转成"**带 file 段的消息**"（不是 `notice.group_upload`），
段里直接给了下载直链。应用现在两种都认：

- 私聊文件：用段里的 `url` 直接下载；
- 群文件：段里没 url 时再调 `get_group_file_url`；
- 事件页里会**像显示消息内容一样显示文件名**（`cherenkov_animation.html（7.1MB）`），
  归档完变成 `已执行：已归档`。

### 图片也算文件

老师发的作业/通知**截图**很常见。SnowLuma 的图片段带直链（`url`）和文件名（`<md5>.png`），
所以图片会和文件一样走归档（受同一个"群文件自动归档"开关与老师名单限制）；
拿不到直链（内联图片）时至少会在事件页显示 `[图片]`，**不会整条消失**。

### 归档目录里只有文件

元数据（发送时间/群号/发送者/科目）写在 `<归档根>/.smartclassroom-meta/<科目>/<文件>.json`，
**科目文件夹里只有真正的文件**（以前会生成一堆同名 `.meta.json`，看着像垃圾）。
旧的 `.meta.json` 仍会被读取（去重与课件索引不受影响），可以手动删掉。

## 文件归档到哪了

目录结构：**`<归档根目录>/<科目名>/<文件名>`**（只到科目一层，不再按日期分层）。

- 科目取自教师映射；**没配科目**时退化为老师姓名；**都不认识**则归入 `未分类`。
- 归档根目录在 **设置 → 文件归档 → 归档目录** 里设置（带「浏览…」文件夹选择器与「打开」按钮）。
  留空则用默认位置，界面上会把**实际生效的路径**显示出来，不会让你找不到文件。
- 默认**只下载教师映射命中的发送者**；打开「下载群里所有人的文件」后，其他人发的也会下载（进对应科目或「未分类」）。
- 每个文件旁边有一个 `<文件名>.meta.json`，记录群号、发送者 QQ/姓名、**科目**、**发送时间**、文件 id 与原始大小。
  上课弹窗就是靠 meta 里的科目判断"当科"的。
  因为目录不再按日期分层，**发送时间要看 meta.json 或文件修改时间**；
  不同天的同名文件会得到 `(1)`、`(2)` 后缀。
- 同一个 `file_id` 不会重复下载；重名自动加序号。

### 归档后同时放进系统"下载"目录

老师常在 QQ 里直接点开文件，而 QQ 只在**自己的下载目录**里找 —— 文件已经躺在那里时，
QQ 会立刻判定"已接收"（用户："你写了以后 QQ 检测到有了就是秒下"）。
所以归档成功后还会**复制一份**到系统下载目录（设置里可关）：

- **Windows**：`%USERPROFILE%\Downloads`；
- **Linux**：读 `~/.config/user-dirs.dirs` 里的 `XDG_DOWNLOAD_DIR`（中文系统里目录可能叫"下载"），
  读不到就退回 `~/Downloads`；
- 重名自动加序号（`name (1).ext`），目录不可写就跳过（不影响归档）。

### 让 QQ 端也"接收"文件

我们直接拉文件直链只是旁观者下载，**老师那边一直显示"未接收"**。
现在归档时会额外调 SnowLuma 的 `download_file`，由 QQ 协议层真正接收；
私聊文件没有直链时用 `get_private_file_url`（群文件才用 `get_group_file_url`）。

### 自己发的消息不会被当成收到的

SnowLuma 对自发消息（self-echo）用 `post_type: "message_sent"` 标记，
应用现在会**直接忽略**这类事件（群消息里 `user_id == self_id` 也一样）——
以前会把**自己发给对方的文件**当成老师发的课件归档。

### 老师信息可以就地修改

老师映射每一行都有「编辑」：点它会把该行填进下面的表单，按钮变成「保存修改」，
改完就地生效（列表立刻刷新，老师映射同时热重载）。以前只能删了重建 ——
用户反馈"无法修改老师信息，删除重建以后还是原科目"。

### 私聊也要过"老师名单"这一关

私聊走的是**独立的陌生人过滤**：老师名单非空时，**名单外的人私聊一律忽略**
（事件页会写明是哪个 QQ，并告诉你去 设置 → 老师映射 里加上它）。
所以"我私聊发了怎么没反应"通常是这两种情况之一：

1. 老师映射里没有发送者的 QQ（名单为空时不过滤，配了就会过滤）；
2. 运行时压根没在跑 —— 检查状态栏是不是"未配置：…"（0.35.6 之前，
   **只监听私聊**的配置会被误判为未配置，那样连 QQ 都不会连）。
